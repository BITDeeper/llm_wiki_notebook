# Harness (智能体运行框架)

**Harness**（智能体运行框架/脚手架/托管框架）是指支撑 AI 模型运行并使其能够完成复杂任务的一整套基础设施和工程逻辑。它标志着 AI 从“单次问答”玩具阶段迈向“生产级系统”的关键范式转移。

在 AI 智能体的构建范式中，业界普遍遵循 **Agent = Model + Harness** 的公式：
- **模型是“大脑”/引擎**：提供基础的智能、推理和知识能力。
- **[[Harness]] 是“身体”/机甲**：决定智能如何被应用，如何与环境交互，以及如何处理不确定性。

再强的引擎，如果没有外骨骼框架来传递动力和执行动作，也无法造出强大的 Agent。

## 起源与发展

- **2026 年 2 月**：HashiCorp 联创 [[Mitchell Hashimoto]] 在博客中率先命名了这一概念。
- **OpenAI 实验**：发布报告称 3 名工程师利用 Codex Agent 在 5 个月内生成了 100 万行生产级代码，展示了 Harness 的潜力。
- **行业共识**：[[Martin Fowler]] 撰写深度长文，Anthropic 发布相关设计指南，确立了 Harness 在 AI 工程化中的核心地位。

## 核心定义与工程难题

随着智能体系统的演进，Harness 的定义也从单纯的“工程脚手架”扩展到了“托管与控制层”，强调为智能体提供稳定、可控、可观测的运行环境。其架构主要解决以下四个工程化难题：

1.  **长时程**：支持以月、年为周期的持续服务，而非单次会话。
2.  **可追溯**：记录建议来源、工具调用链路和知识库版本，确保每一步都有据可查。
3.  **可执行**：不仅生成文本，还能连接外部设备、系统和业务流程。
4.  **可治理**：内置权限管理、数据脱敏、审批流程和审计机制，确保系统在合规边界内运行。

## 比喻：F1 赛车与驾驭者

[[MiniMax]] 首席架构师 [[阿岛]] 曾用“F1 赛车”生动比喻 Agent 与 Harness 的关系：
- **Agent**：马力全开的 F1 赛车（模型能力）。
- **[[Harness]]**：专业的车身结构与赛道系统（工程架构）。
- **企业环境**：应为 Agent 打造适配的车身与专业赛道。

**现状误区**：很多企业把 F1 赛车开在乡镇公路上，还要求它遵守家用车的规则。这反映了思维模式的滞后——在 [[Agent Native]] 时代，人类和企业的角色必须从“操作者”转变为“驾驭者（[[Harness]]）”，负责设定目标、提供资源、监督结果，而非束缚 Agent 的手脚。

## 核心组件

一个典型的 [[Harness]] 包含以下要素：

### 1. 基础编排与逻辑
- **系统提示词**：定义模型的角色和行为准则。
- **工具定义与调用**：管理和调度模型与外部工具（API、数据库、文件系统）的交互。
- **重试逻辑**：处理失败和错误的策略。
- **子代理协调**：多个子任务之间的调度与通信（参见 [[多agent分层编排]]）。
- **生命周期钩子**：任务开始、结束、中断时的触发器。

### 2. 记忆与上下文
- **上下文管理**：如何截断、保留和检索历史信息。
- **记忆管理**：处理短期记忆（上下文窗口）和长期记忆（向量数据库、RAG）的存储与检索。

### 3. 执行环境与托管
- **Skills 系统**：定义、存储和执行复杂任务流程的“技能包”。
- **沙箱环境**：提供安全、隔离、可弹性伸缩的代码执行环境。
- **托管控制层**：在高级架构中，Agent 不再拥有直接执行权，而是由 Harness 层进行路由、策略校验和沙盒托管。

## 架构演进：从“裸奔”到“托管”

随着 AI 智能体从简单的工具调用发展为复杂的自主系统，Harness 的架构也在不断进化：

### 1. 逻辑链增强（如 [[hermes-agent]]）
侧重于让 Agent 的“大脑”更聪明、逻辑更严谨，通过自进化和架构设计提升性能，但 Agent 本身仍拥有较大的执行权。

### 2. 托管框架（如 [[claude-managed-agents]]）
Anthropic 提出的企业级智能体托管框架，强调通过标准化 Harness 为通用智能体提供企业级运行底座。其核心思想是**“管束”**：
- **路由**：确定任务流向。
- **策略校验**：检查权限和安全合规性。
- **沙盒托管**：在隔离的环境中执行实际操作。
这种模式通过牺牲部分自主性，换取了系统的可控性、安全性和可维护性。

### 3. 透明化托管（如 [[scienceclaw]]）
[[紫东太初]] 推出的 AI4S 平台采用了类似的 Harness 架构，并进一步实现了 **[[执行透明度]]**。其特点在于使得托管过程不再是黑盒，而是全链路实时可观测的，解决了传统“裸奔”模式（如 [[openclaw]]）面临的部署难、不可控等问题。

### 4. 协同架构（如 [[wiseclaw-2.0]]）
在复杂的系统中，Harness 通常与 [[openclaw]] 协同工作：
- **OpenClaw**：负责“连接与调度”，解决“能不能做”的问题。
- **Harness**：负责“治理与控制”，解决“稳不稳、能不能管”的问题。

## 应用场景

虽然早期的 Harness 讨论多集中在代码生成领域，但其在医疗、金融等高风险行业的价值尤为显著。例如，在医疗场景中，Harness 通过 [[三层流水线]] 和 [[心跳引擎]]，将不可控的模型输出转化为可审计、可干预的业务流程。

## 战略意义

随着模型能力的趋同，AI 行业的竞争维度正从“模型智商”转向“工程落地”，即 [[Harness]] 的能力。

### 1. 性能影响巨大
[[Harness]] 的质量对最终性能的影响甚至超过了模型本身的参数量。
- **案例**：工程师 Can Bölük 仅通过改变编辑格式（不动模型），就让 GPT-4 Turbo 的准确率从 26% 飙升到 59%。
- **结论**：同一个模型，配上不同的 [[Harness]]，性能差距可以高达一倍以上。

### 2. 人类成为瓶颈
工程师构建 [[Harness]] 的过程，本质上是将人类的工作方式蒸馏成 Skills 和代码，让 AI 接管执行。如果人类思维仍停留在“手把手教”而非“设计赛道”，就会成为 Agent 发挥效能的瓶颈。

### 3. 双向飞轮效应
[[minimax]] 提出了“Model + Harness”的双向飞轮模式：
- **正向**：模型为 [[Harness]] 优化底层能力（如工具调用准确性、长上下文一致性）。
- **反向**：[[Harness]] 产品在真实场景中验证需求，产生数据反馈给模型，指导模型迭代。

## 技术挑战与优化

### 1. 云端沙箱难题
构建高性能 [[Harness]] 的最大难点在于**云端沙箱**：
- 需要支持高并发（每分钟数万实例）。
- 需要极低延迟（20-80ms 启动）。
- 需要严格的安全隔离。
这通常需要与云厂商（如腾讯云、阿里云）深度合作，利用其底层基础设施（如容器服务、无服务器架构）来实现。

### 2. 自动化优化
传统的 [[Harness]] 工程高度依赖人工经验（手动写提示词、调接口、看日志猜问题）。[[Meta-Harness]] 等新框架正在尝试将这一过程自动化，通过分析 **[[完整执行轨迹]]** 来自动诊断和修复 [[Harness]] 中的缺陷。
