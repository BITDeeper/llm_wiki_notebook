# 布局回流

**布局回流**（Layout Reflow / Reflow），是指浏览器在渲染页面时，为了确定元素的位置和几何信息（如宽、高、位置），而重新计算页面布局的过程。

## 触发条件
当页面中的元素发生了影响布局的变化，或者 JavaScript 代码查询了某些布局信息时，浏览器会触发回流。常见的触发操作包括：

-   添加或删除可见的 DOM 元素。
-   元素的位置、尺寸（如 `width`, `height`）发生变化。
-   浏览器窗口尺寸改变（`resize`）。
-   **读取布局信息**：这是性能优化中常被忽视的点。调用如 `offsetHeight`, `getBoundingClientRect()`, `getComputedStyle()` 等 API 时，如果浏览器之前的布局已失效，浏览器必须强制执行一次同步的布局计算以返回准确数值。

## 性能影响
布局回流是非常消耗 CPU 的操作。在复杂的页面中，一次回流可能涉及计算数千个节点。

-   **强制同步布局（Forced Synchronous Layout）**：如果在 JavaScript 中频繁读写布局属性（例如在循环中先读取 `offsetHeight` 再修改 `style.height`），会导致浏览器反复触发回流，严重阻塞主线程。
-   **帧率影响**：浏览器渲染一帧的预算约为 16.67ms（60fps）。如果回流耗时过长（如超过 30ms），就会导致页面掉帧、卡顿，甚至出现“脚本执行时间过长”的警告。

## 解决方案

### 传统优化手段
-   **批量读写**：使用 `requestAnimationFrame` 或将 DOM 操作集中处理，减少读写交替。
-   **避免逐条修改样式**：通过切换 `class` 或使用 `cssText` 批量修改样式。
-   **虚拟列表**：只渲染可视区域内的元素，减少 DOM 节点数量。

### 根本性解决方案：Pretext
[[Pretext]] 提出了一种根本性的解决思路：**完全绕过 DOM 测量**。

通过将布局计算从浏览器内核转移到 JavaScript 的纯数学运算，[[Pretext]] 消除了对 `getBoundingClientRect` 等会触发回流的 API 的依赖。这使得即使在处理海量文本（如 500 条评论）时，布局计算也能在微秒级（0.10ms）完成，从而彻底避免了回流带来的性能瓶颈。
