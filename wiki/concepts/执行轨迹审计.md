# 执行轨迹审计

执行轨迹审计（Execution Trace Auditing）是一种不仅关注 Agent 最终输出，还深入检查其执行过程（工具调用、日志、状态变更）的评测方法。它通过截图、CLI/MCP 操作卡片、文件变化、系统状态和 App 侧结果共同构成可审计证据链，用于验证 Agent 任务完成情况并支持失败归因。

## 必要性

前沿模型可能会通过「捷径」（如幻觉生成看似正确的答案）来通过评测。仅看结果的评测方式会系统性高估模型能力。执行轨迹审计解决两个关键问题：

1. **验证**：确认 Agent 是否真的完成了任务，而非仅声称完成
2. **归因**：当任务失败时，精确定位是规划错误、GUI 操作错误、工具调用失败还是环境不稳定

## 构成要素

一条完整的执行轨迹包含：

- **截图序列**：GUI 操作过程的视觉快照
- **CLI/MCP 操作卡片**：每步命令行和工具调用的结构化记录
- **文件变化日志**：文件系统层面的创建、修改、删除记录
- **系统状态快照**：设备设置、权限状态的变更记录
- **App 侧结果**：邮件发送确认、日历事件创建等 App 层面的实际产出

[[claw-eval]] 引入了三条独立的证据链来进行审计：

1. **执行轨迹**：Agent 的具体操作步骤
2. **服务端审计日志**：记录了 API 调用详情和潜在的错误
3. **环境快照**：执行后的系统状态，用于验证是否发生了预期的变更

## 实验证据

对照实验表明，如果屏蔽审计日志和环境快照，仅凭对话记录评分，LLM Judge 会漏掉 **44% 的安全违规** 和 **13% 的鲁棒性问题**。这证明了过程审计对于获得可信评测结果至关重要。

## 与相关概念的关系

执行轨迹审计是[[可验证副作用]]的实现手段，与[[场景白盒化推理]]的理念一脉相承——都是将 AI 执行过程从不可见"黑盒"转变为可见、可干预"白盒"。在[[phoneharness]]中，执行轨迹审计是 Bench 评测体系的核心基础设施。
