# DualPath

[[DualPath]] 是由 [[DeepSeek]] 联合北京大学和清华大学提出的针对智能体推理优化的双路径 KV-Cache 加载架构。该架构旨在解决大规模 [[kv-cache]] 从外部存储读取时产生的 I/O 瓶颈问题，通过将数据加载与计算过程并行化，显著提升了智能体系统的推理吞吐量。

## 核心原理

DualPath 的核心创新在于实现了 [[计算与存储解耦]]。传统的推理架构是串行的：计算单元必须等待数据通过 PCIe 总线完全加载到显存后才能开始计算。DualPath 引入了 **Storage-to-Decode** 通路，使得数据加载（回忆）与计算（思考）可以并行进行，类似于视频播放的“边下载边播放”。

### 双路径加载机制

DualPath 的核心洞见在于：**KV-Cache 的加载不必以预填充为中心**。系统在两条路径间动态选择，重新分配了网络负载，缓解了预填充侧的带宽压力，实现了集群存储带宽的全局池化与动态负载均衡。

- **路径 A（传统）**：存储 → PE（预填充引擎），缓存直接读入预填充引擎。
- **路径 B（新增）**：存储 → DE（解码引擎） → PE，缓存先读入解码引擎的缓冲池，再通过 [[RDMA]] 传输给预填充引擎。

### 关键技术

1.  **块式流处理**：将庞大的 KV Cache 切分成小块。当计算单元处理第 N 块时，存储单元预加载第 N+1 块。
2.  **PD分离架构优化**：在 Prefill-Decode 分离架构的基础上，解决了预填充端网卡过载而解码端网卡闲置的资源失衡问题。

## 技术架构

DualPath 系统主要由三部分组成，协同工作以最大化带宽利用率：

1.  **推理引擎**：每个引擎管理一块 GPU，严格区分为预填充（PE）和解码（DE）。
2.  **流量管理器**：负责 H2D/D2H 拷贝、引擎间传输以及 [[SNIC]] 存储读写。
3.  **中央调度器**：担任“大脑”角色，实时决策每一条请求该走哪条路。

### 网络与调度优化

为了解决“绕路”加载可能带来的网络冲突，DualPath 采用了两套优化方案：

1.  **以 [[CNIC]] 为中心的流量管理**：
    强制所有流量通过配对的 CNIC 走 GPUDirect RDMA 路径。在 InfiniBand 或 RoCE 网络中，利用虚拟层（VL/TC）技术，将推理通信设为“最高优先级”并预留 99% 带宽，让缓存搬运只能在间隙中“蹭”带宽。

2.  **自适应请求调度器**：
    调度器会监控每个节点的磁盘队列长度和 Token 数。系统会优先将任务分配给 I/O 压力较小且计算负载较轻的节点，从根本上避免单侧网卡或单点计算资源的拥塞。

## 性能表现

根据 DeepSeek 发布的论文数据（基于 660B 规模的生产级模型实测），DualPath 在智能体场景下带来了显著的性能提升：

*   **离线推理**（强化学习 Rollout）：吞吐量最高提升 **1.87倍**。
*   **在线服务**：每秒智能体运行次数（吞吐量）平均提升 **1.96倍**。
*   **延迟优化**：在高负载下，首字延迟（TTFT）大幅优化，而 Token 间的生成速度（TPOT）几乎不受任何干扰。
*   **扩展性**：在 1152 块 GPU 的集群上支持 4.8 万个并发智能体，并实现了线性扩展。

## 应用场景

DualPath 特别适用于长上下文、多轮交互的 [[智能体]] 场景，例如 [[openclaw]] 等需要频繁读写大量上下文（数百万 token）的编码或任务执行工具。在这些场景中，[[缓存-计算比率]] 极高（约 22GB/PFLOP），I/O 带宽而非算力成为主要瓶颈。

## 与 DeepSeek V4 的关系

该论文暗示 [[DualPath]] 可能是 [[DeepSeek V4]] 基础设施的关键组成部分，与 [[DeepGEMM]] 等计算优化技术共同构成了 V4 的性能护城河。

## 局限性

*   **硬件依赖**：高度依赖特定的硬件拓扑（如 GDRDMA、高带宽网卡）。
*   **未覆盖工具调用**：目前的优化主要针对模型推理，未包含智能体调用外部工具（如代码解释器、数据库查询）的延迟。
