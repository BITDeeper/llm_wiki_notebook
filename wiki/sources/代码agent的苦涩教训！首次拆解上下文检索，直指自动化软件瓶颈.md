# 代码Agent的苦涩教训！首次拆解上下文检索，直指自动化软件瓶颈

## 概述
本文报道了南京大学与 UCL 团队发布的首个面向过程的代码上下文检索评测基准 [[contextbench]]。该基准通过引入由专家标注的“[[黄金上下文]]”，将评测重点从单纯的“结果导向”（是否修好代码）转向“过程导向”（是否精准定位并使用了关键代码），揭示了当前代码智能体在检索策略、架构有效性及信息整合方面的深层问题。

## 核心发现

### 1. 评测范式的转变
传统的 [[swe-bench]] 等基准主要关注端到端（End-to-End）的成功率，但这存在“黑盒”缺陷：无法判断 Agent 是真正理解了代码库，还是通过试探或运气修好了 Bug。[[contextbench]] 通过追踪 Agent 的中间步骤，实现了 [[过程可解释性]]，将“找上下文”和“用上下文”拆开评估。

### 2. “苦涩的教训”：复杂架构的失效
实验数据表明，复杂的 Agent 架构（如基于图的检索、复杂向量库）在上下文检索质量上并未显著优于简单方案（如 mini-SWE-agent）。这印证了 [[苦涩的教训]]：在模型能力尚未突破时，过度的工程化堆砌收益递减。

### 3. 模型的检索策略缺陷
- **高召回低精确**：顶尖模型（如 GPT-5）普遍采用“宁滥勿缺”的策略，导致引入大量噪音干扰推理。
- **策略分化**：
    - **GPT-5**：“大口吞”（少次多量），平均 5.87 轮检索，每步阅读 119 行。
    - **Devstral 2**：“小步跑”（多次少量），平均 22 轮检索，每步仅读 12 行，成本极高。

### 4. 致命的“关键词陷阱”
Agent 极易被表面关键词误导，陷入“隧道视野”。例如 [[openhands]] 在处理 Django 多数据库 Bug 时，因 MySQL 关键词而忽略了真正出问题的 SQLite 模块。

### 5. 信息整合瓶颈
研究发现存在“过目即忘”现象：Agent 在中间步骤成功检索到了黄金上下文，但在最终生成补丁时却未能有效利用。这种“检索成功但推理失败”的现象被称为 [[信息整合瓶颈]]。

## 意义
[[contextbench]] 的发布标志着代码 Agent 评测进入了新阶段，迫使行业不仅要关注代码生成能力，更要重视代码定位与检索的稳定性与精确性。
