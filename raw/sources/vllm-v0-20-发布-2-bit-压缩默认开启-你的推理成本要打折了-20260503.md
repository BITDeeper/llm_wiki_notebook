4 月底，vLLM 悄悄发布了 v0.20.0。没有发布会，没有大新闻——但这个版本把两项此前只活在论文里的技术默认开启，直接影响到所有部署大模型的工程师。显存，永远不够用 💸去年你在朋友圈刷到这条消息：某团队 4 张 H100 跑 DeepSeek-R1，推理速度勉强能用。今年这个消息变成了：某团队 2 张 H100 跑 DeepSeek-V4，速度还快了 30%。为什么？不是因为显卡变便宜了，而是因为推理框架更聪明了。大模型推理的核心瓶颈从来不是算力。GPU 的矩阵计算能力现在已经过剩——真正卡脖子的是显存。更具体地说，是 KV Cache。每次模型生成一个 token，它都需要把之前所有 token 的中间状态存在显存里，方便下一步计算。这块内存就叫 KV Cache。处理一段 128k 的上下文，KV Cache 可能吃掉几十 GB 显存——直接把其他事情全挤走了。vLLM 三年前用 PagedAttention 解决了 KV Cache 的碎片化问题，让显存不再"内存泄漏式浪费"。现在 v0.20.0 带来的两项技术，解决的是另一个问题：能不能把 KV Cache 本身压得更小？答案是：可以，而且损失比你想象的小得多。TurboQuant：谷歌压箱底的量化手法 🔬TurboQuant 是谷歌 DeepMind 在今年 ICLR 2026 上发表的论文成果。核心想法其实不难理解——把 KV Cache 的数值从 16-bit 浮点数压缩成 2-bit 整数，显存占用直接缩小 8 倍。问题当然是：压缩之后，精度会不会垮？传统量化方法确实会垮。直接把浮点数四舍五入成整数，误差会在每一步推理里累积，最后导致输出乱说话。TurboQuant 的聪明之处在于，它在量化之前先做了一步随机正交旋转。什么意思？想象一下，你有一堆数字，有些特别大，有些特别小，分布很不均匀——这种情况下量化肯定损失大。TurboQuant 做的事情，就是在量化之前把这些数字"旋转"到一个新的坐标系里，让它们的分布变得更加均匀、更接近正态分布。旋转之后再量化，每个维度承受的误差就小得多。具体来说，这套流程分三步：第一步，固定随机正交旋转：对 KV 向量施加一个预先固定的旋转矩阵，让数值分布标准化。这个旋转矩阵不需要训练，直接根据数学原理生成。第二步，标量量化：用预计算好的固定码本把旋转后的坐标映射到低精度整数。同样不需要数据集校准。第三步，QJL 变换：对残差误差做一次 Quantized Johnson-Lindenstrauss 变换，保证内积计算（attention score 的核心）的几何精度。整个过程没有再训练，没有校准数据集，拿来即用。实测数字很好看：在 3-bit 模式下，LongBench 和"大海捞针"长文本检索的表现与 FP16 几乎持平，属于"绝对质量中立"。2-bit 模式有轻微下降，但对延迟极度敏感的场景完全可以接受。H100 上 4-bit 模式下，attention logit 计算速度实测达到 8× 加速。这个 8× 数字是什么概念？对于处理 128k 上下文的推理任务来说，原本光是 attention 计算就要占满 GPU 的一大块时间。8× 的 logit 加速意味着同等时间内能处理多出几倍的序列位置，整体推理延迟可以砍掉一大截。对于实时语音转文字、长文档问答、会话式 Agent 这类对响应速度有要求的应用，这是实实在在的降本增效。另一个值得关注的角度是并发能力。KV Cache 压缩 4× 意味着同样的显存可以同时维持 4 倍的并发对话上下文。一张 80GB 的 H100，原本 KV Cache 撑死能服务 10 个并发长上下文请求；压缩之后理论上能服务 40 个。这对 B 端服务的成本控制影响巨大——同样的服务质量标准，需要的卡数可能直接减半。vLLM v0.20.0 把这套东西打包成了一个新的 attention 后端，默认集成，支持 FlashAttention 3 和 4 两种 prefill 路径。你什么都不用改，升级版本就开始受益。FlashAttention 4 + MLA：专门给 DeepSeek 开后门 ⚡同一个版本里还有另一件大事：FlashAttention 4 正式成为 MLA Prefill 的默认后端。MLA 是什么？这是 DeepSeek 系列模型（R1、V4）使用的注意力机制，全称 Multi-Head Latent Attention。它的设计思路是用"矩阵吸收"压缩 KV 的表示维度，让 KV Cache 天然就比标准 MHA 小很多。但这带来了一个工程难题：MLA 的计算过程和标准 Multi-Head Attention 不一样，你不能直接套 FlashAttention 的标准实现。早期 vLLM 的处理方式是把 MLA 当作 MQA（Multi-Query Attention）来凑合跑，效率差，内存也没有完全发挥出来。后来版本开始做专用的 MLA Kernel，但效果仍然受限于 FlashAttention 2/3 的能力边界。v0.20.0 里，vLLM 完成了 FA4 与专用 MLA Kernel 的深度整合：Prefill 阶段：FA4 接管，支持 head-dim 512 和 paged-KV 结构，在 SM90+（H100、H200、Blackwell）架构上充分利用硬件。KV Cache 有效容量相比早期 MQA 处理方式提升达 10×。这里的 10× 需要解释一下。早期 vLLM 处理 MLA 的方式是把它"展开"成等价的 MQA 形式再计算。这个过程会把 MLA 压缩过的 KV 向量还原成完整尺寸，等于把 DeepSeek 辛苦做的内存压缩工作白费了。新版的专用 MLA 核保持 KV 的压缩表示不展开，直接在压缩空间里算注意力，这才是 MLA 设计的正确打开方式。Decode 阶段：专用 FlashMLA 核接管，针对 memory-bound 特性做了专项优化。Decode 是典型的内存带宽瓶颈场景——每生成一个 token 只做少量矩阵计算，但要从显存里读大量的 KV Cache。FlashMLA 针对这个特点做了 IO 优化，减少不必要的显存读写来提速。从用户角度来说，效果最直接体现在：运行同样的 DeepSeek-V4-Pro，单卡能 serve 的 batch size 明显增大，或者 TP（Tensor Parallel）需要的卡数减少。之前四卡才能稳定跑的任务，现在两卡就够了。这不是夸张，是 MLA 原本的设计意图加上正确实现共同带来的结果。FA4 目前对硬件有要求，SM90+ 是标配。如果你跑的是 A100（SM80），框架会自动回退到 FA3 路径，不会报错，但也拿不到最新的性能红利。买了 H100 还没升级 vLLM 的朋友，这次真的别再等了。版本快照：其他不容忽视的更新 📦v0.20.0 这次同时塞进来了好几个独立功能，单独拎出来都值得看一下。DeepSeek V4 初步支持。Pro 和 Flash 两款模型都跑通了，配合 FA4 + TurboQuant 用效果最佳。vllm launch render 命令。这是个很有意思的方向——把多模态预处理（图片编码、视频帧解码等高 CPU 消耗操作）从 GPU 推理进程里彻底分离出来。你可以在没有 GPU 的机器上跑 render 进程做预处理，把结果通过队列送给 GPU 机器跑推理。对于图文混合应用，这能显著降低 GPU 的等待时间。FlexKV 分布式 KV 卸载。进一步增强了 KV Cache 的 Disaggregated Serving 能力，允许把 KV Cache 卸载到 CPU 内存、SSD 或远程存储。Prefill 和 Decode 两个阶段可以部署在不同机器上，KV Cache 在中间传递。这是大规模服务化部署的必备选项。Python 3.14 + HuggingFace Transformers v5 兼容。技术栈升级的自然节奏，但如果你跑的是老版本 Transformers，这次需要注意一下依赖。快速上手：从安装到开启 TurboQuant 💻升级很简单。先安装 v0.20.0：pip install vllm==0.20.0如果你用的是 CUDA 13.0（建议升级以获得最佳性能）：pip install vllm==0.20.0 --extra-index-url https://download.pytorch.org/whl/cu130TurboQuant 2-bit KV Cache 是自动开启的，无需额外配置。如果你想显式指定 KV Cache 的量化精度：vllm serve Qwen/Qwen3-8B \  --kv-cache-dtype "auto" \  --max-model-len 128000开启 FlexKV 分布式 KV 卸载（Disaggregated Serving 场景）：vllm serve deepseek-ai/DeepSeek-V4-Pro \  --kv-transfer-config '{"kv_connector":"FlexKVConnectorV1","kv_role":"kv_both"}' \  --tensor-parallel-size 4把多模态预处理分离到 CPU 节点：# 在 CPU 机器上启动 render 进程vllm launch render --model Qwen/Qwen2-VL-7B-Instruct --port 8001# GPU 机器上的推理进程通过 render 地址接收预处理后的数据vllm serve Qwen/Qwen2-VL-7B-Instruct \  --render-url http://cpu-node:8001 \  --tensor-parallel-size 2从 PagedAttention 到 TurboQuant：vLLM 在解决什么问题 🗺️值得花一点时间看看这个项目的脉络，因为它揭示了推理层目前最核心的工程矛盾。2023 年，vLLM 在 UC Berkeley 诞生，核心贡献是 PagedAttention。那时候的问题是：KV Cache 的内存碎片化太严重，显存利用率极低，大量显存被内部碎片"吃掉"。PagedAttention 借鉴操作系统的内存分页思路，把 KV Cache 拆成小块按需分配，一举解决了碎片问题。这个想法影响深远，基本上所有后来的推理框架都吸收了类似的思路。vLLM 凭这篇论文一炮而红，2024 年被捐献给 Linux Foundation，2025 年成为 PyTorch Foundation 的托管项目。目前贡献者超过 2000 人，跑在数十万张 GPU 上。PagedAttention 解决了"怎么用好手头的显存"的问题。TurboQuant 解决的是"怎么让 KV Cache 本身更小"的问题。这是两个层次的优化，现在合并在了 v0.20.0 里。如果你回想一下 vLLM 这三年的迭代路径：PagedAttention（碎片管理）→ Continuous Batching（吞吐率）→ 分布式推理（多卡并行）→ 投机解码（延迟）→ FP8/AWQ 量化（模型压缩）→ MoE 支持（架构扩展）→ TurboQuant + FA4（KV 压缩 + 架构专项优化）——每一步都是在解决上一步解决完之后暴露出来的新瓶颈。这是个很健康的工程项目的样子。换一个角度想：大模型能力的上限取决于模型本身，但大模型能力的落地效率几乎完全取决于推理框架。更快、更省显存的推理框架，能让同样的算力预算服务 2 倍、5 倍甚至 10 倍的用户。从这个维度来看，vLLM 这类项目在整个 AI 生态里的位置，不亚于 Llama 和 GPT 本身。有意思的一点是，vLLM 现在已经不只是"一个工具"，它已经变成了一套推理基础设施标准。各大云厂商、芯片厂商（NVIDIA、AMD、Qualcomm、Intel）都在往 vLLM 里贡献硬件支持。这意味着任何一个你在 vLLM 里训练出来的使用习惯，都可以在不同硬件平台上平移——这对工程团队的架构稳定性来说是件非常重要的事。你真的需要升级吗？💡如果你现在在生产上跑的是 vLLM 0.18 或者更早的版本，v0.20 的这次升级有几个判断依据：跑 DeepSeek V4 系列？强烈建议升级。FA4 + 专用 MLA Kernel 对这个家族的加速效果最显著，老版本跑 DeepSeek V4 是在"将就"。上下文长度经常超 32k？建议升级。TurboQuant 的收益在长上下文场景下最突出，KV Cache 本来就大，压缩比例带来的显存节省越明显。跑的是 Llama/Qwen 等标准 MHA 架构、上下文不长？升级没坏处，但收益没那么戏剧性。TurboQuant 照样有效，只是 FA4 的 MLA 专项优化跟你关系不大。有多模态需求，且预处理是 CPU 瓶颈？vllm launch render 的分离部署模式值得认真研究。主要的兼容性注意点：CUDA 最低要求 13.0，Python 3.12+，HuggingFace Transformers 要升到 v5。如果你现在的环境比较老旧，在升级 vLLM 之前先把这几个依赖对齐。项目主页：https://vllm.aiGitHub：https://github.com/vllm-project/vllmv0.20.0 Changelog：https://github.com/vllm-project/vllm/releases/tag/v0.20.0
