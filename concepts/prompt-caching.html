Prompt Caching (提示词缓存) §

提示词缓存（Prompt Caching）是大语言模型（LLM）的一种优化技术，旨在通过缓存已处理的上下文（如 System 指令、工具定义、长文档背景），避免在后续请求中重复计费和重复计算。这对于降低长对话或复杂 agent-loop 任务的成本和延迟至关重要。

核心原理 §

Prompt Caching 采用“前缀匹配”策略。当启用缓存发送请求时，系统会检查从用户指定的缓存分隔点往前的提示词开头部分（前缀），判断这部分内容是否在最近的请求中已经被处理并存储过。

  • 命中缓存：直接复用之前的计算结果（KV Cache），时间和成本大幅降低。
  • 未命中：完整处理整个提示词，并在生成回复时将开头部分写入缓存。

在 agent-loop 架构中，每次循环都需要将完整的对话历史发送给模型。随着对话进行，Token 数量呈线性增长，导致计算成本呈平方级增长。Prompt Caching 通过复用不变的前缀，将长对话的成本从 平方级增长 降至 线性级增长。

TTL (生存时间) 策略 §

TTL 决定了缓存内容的有效期。在 claude-code 的实践中，TTL 的长短直接决定了用户体验和成本：

  • 1 小时 TTL (ephemeral_1h)：适合长上下文会话，允许用户在思考、调试期间保持缓存，减少重建频率。
  • 5 分钟 TTL (ephemeral_5m)：极其激进，用户稍作停顿（如思考思路或休息）就会导致缓存失效。

成本结构 §

提示词缓存的成本结构具有显著的不对称性：

  • 写入成本：将新内容写入缓存。
  • 读取成本：从缓存中读取内容。

根据 claude-code 的定价，缓存写入成本是读取的 12.5 倍（写入约为 base input 的 2 倍，读取仅为 1.25 倍）。因此，频繁的缓存失效和重建会导致总 Token 消耗呈指数级增长。

常见陷阱与失效条件 §

Prompt Caching 对前缀的变化非常敏感。以下操作通常会导致缓存失效，从而引发性能回退：

  • 中途更换模型：切换不同的模型版本或供应商。
  • 修改权限配置：改变 System Prompt 中的安全设置。
  • 改变工具列表：在 agent-loop 中动态增删或调整 MCP 工具的顺序。
  • 修改历史记录：对之前的对话内容进行编辑或摘要。
  • 策略变更风险：服务商可能会在后台调整 TTL 策略（如从 1 小时静默回退至 5 分钟），导致用户成本意外激增。
  • 功能绑定：某些高级缓存策略可能与 telemetry（遥测）或 experiment-gates（实验性功能门控）绑定，强制用户在隐私和性能之间做选择。

实践案例 §

openai 在 codex 中大量使用了 Prompt Caching 技术。团队曾发现早期的 MCP 工具集成存在 Bug，导致工具列表顺序不稳定，进而引发缓存频繁失效。修复这一 Bug 后，系统性能得到了显著提升。

与 Compaction 的区别 §

compaction 旨在解决上下文窗口有限的问题，通过压缩历史内容来腾出空间；而 Prompt Caching 旨在解决计算成本问题，通过复用计算来节省资源。两者常结合使用以优化 Agent 性能。
